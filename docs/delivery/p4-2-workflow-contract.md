## Application state versus lifecycle

Desktop accepts transient `pre_project`, persisted preliminary `zero`, and full `project`. Save converts `pre_project` to `zero`; `zero` stays `zero`; full remains `project` (`Application_New_Form.cs:6902–6925`). The direct-full and zero-to-project paths exist. These are application-form states, not funding/approval decisions.

Desktop preliminary creation also writes an `On Hold` state-history row (:4217). Full conversion/direct-full writes `Waiting`, updates current-state flags and creates initial task assignments (:4287–4302). Those side effects overlap P4.3. P4.2 may implement preliminary/full application state with an explicit tested boundary, but must not claim complete desktop lifecycle parity while these history/task effects remain deferred. Never expose arbitrary state/history/score writes as ordinary editable payload. Full-to-preliminary rollback and review/funding transitions require the P4.3 transition contract.

## Rehabilitation

`ApplicationRehab_Form.cs:365–469` requires an existing selected project/beneficiary and question validation. Header `op_microproject_rehab` has project relation, PropertyOwnership and PropertyArea (both text, length 200), Created_By/Edited_By historical strings. A rehabilitation save also updates the project's post-funding street/address through `Update_MP_Place`; that scope must be explicit and transactional if enabled. Do not fabricate a legacy user identity for the current web actor; use web audit metadata.

`rehabquestion.Type` is catalog grouping metadata returned as Q_Type by `Classes/RehabApplication.cs`; it is not a new application lifecycle enum. Render catalog labels/types from the source-qualified catalog. Each `op_microproject_rehab_answer` relates rehabilitation header, question and answer and stores Note (text), Number (int), Price (double), Result (text). Multiple rows for one question carry their own identities. Do not assume Result is a computed numeric total: desktop reads and saves its textbox as text.

The validator (`ApplicationRehab_Form.cs:510–557`) explicitly makes original question IDs 1, 4 and 11 optional; original IDs >=9 otherwise have maximum one answer, earlier IDs maximum ten. These conditions use source **raw** question IDs, never globally allocated canonical IDs. There is a desktop defect: the optional-question branch uses `break`, which skips the remaining inner group rather than only that question. Document this discrepancy; use the explicit per-question optional/max rules as the implementation interpretation, and leave exact parity with the accidental group skip unresolved rather than silently claiming it. Catalog rows without original IDs need an explicit validation policy; do not guess that their new IDs carry these meanings.

The desktop defaults empty Number/Price to zero and formats price to two decimals when loading (`:275–286`, `:437–441`). Do not round unchanged imported prices just to reproduce display formatting. Existing headers may be multiple per project: `Get_Rehab_ID` selects one without ordering and update targets all matching project IDs. The web must select an explicit header identity; never invent a one-header uniqueness constraint or silently merge existing headers.

## Numeric, date, draft and authorization contract

The approved physical schema stores requested amount and rehabilitation price as double, rehabilitation number as int, request date as date, property area/debt amount/result as text, and course dates/work years as text. Validate newly supplied values for these actual types and finite numeric range. Preserve unchanged null, zero, empty text, sentinel dates, text spelling and historical floating values. No currency conversion, blanket two-decimal rounding, inferred currency or new age/amount eligibility rule is authorized by this source trace.

Existing approved tables cover these payloads; no new business table is intrinsically required. Durable drafts have no approved relational table. The root-selected implementation is encrypted private file drafts, with no new physical tables. Such drafts must be scoped to current account, city/source, form/record identity, bounded in size, written atomically and guarded against stale overwrites and path manipulation. Recheck access on restore/save/delete and again when committing; encrypted storage does not replace authorization. Preserve original edit version through draft restore and validation recovery. Draft recovery must not upgrade a stale payload to a fresh version token. Document retention and key-loss behavior and avoid plaintext business values in logs or committed fixtures.

Use explicit applications read/manage grants per city, not legacy menu visibility or people/project read as mutation authority. Desktop rehab role checks omit some roles; omission is not permission. Real staff-role mapping remains separate from synthetic local grants. A committed aggregate must validate its person, project, catalog and child ownership inside its write boundary; reject forged child IDs, cross-source links, stale edits and duplicate retries. Historical authors remain immutable evidence.

## Acceptance boundaries

A minimal project form with role links and add-on questionnaires is an incremental P4.2 slice, not complete full-intake parity if family/support/material/story/yes-no validation or lifecycle side effects are omitted. Record implemented versus deferred sections explicitly. Required checks include preliminary/full creation and promotion, touched-only legacy saves, dependent catalog tampering, question-answer mismatch, optional/max rehab questions, multiple existing headers, unchanged floating/sentinel values, Arabic/RTL input, private draft access/recovery, stale restore, revoked permissions and request retry/concurrency. Five-city data parity and P4.3 lifecycle acceptance remain separate.
