# Phase 3 import, file access and reconciliation contracts

Prepared 17 October 2026. Status: implementation contract proposal for P3.1–P3.3, pending accepted P3.0 physical schema and independent implementation review. No importer, storage adapter or reconciliation execution is delivered by this document. This does not approve new domain migrations or production access.

The accepted preservation schema, `phase-1/mapping-spec.md`, `phase-1/preservation-spec.md`, the unified-account revision and the Phase 3 execution backlog govern this contract. Existing typed city tables are evidence, not the final shared operational business model. Future physical support for checkpoints, mapping and file catalogs must be reviewed against these requirements rather than inferred from a JSON field or this document.

## Immutable inputs and identity

Each import freezes a manifest of all five source snapshots, SQL/archive/DDL hashes, source and city identifiers, extractor version, restore server/settings, charset/collation, timezone, approved mapping version/hash and target schema version. Validate these before reading a checkpoint. A changed snapshot, mapping, extractor or incompatible target schema starts a separate run; no continuation under an old checkpoint. Expected counts come from the matching manifest, never a hardcoded 10,512-project baseline.

For keyed records, persist the full versioned length-prefixed key in declared column order with column names, source types, null tags and exact value bytes. Integer/decimal payloads use exact strings or binary, never floating JSON numbers. Store a SHA-256 index only alongside full-byte equality checks; a digest collision blocks the run. Source collation determines parent lookup identity; it does not license trimming or normalization of retained bytes. Every lookup is qualified by source, table and snapshot.

For keyless records, use the immutable SQL member hash plus statement ordinal and tuple ordinal, or a separately frozen extraction manifest with immutable ordinals. Payload digest verifies content but never identifies a duplicate on its own. Two equal rows at different ordinals map to two distinct preservation records and two operational occurrences where mapped. Never assign identities from unordered SELECT results. Typed preservation record IDs may be locators only after independently verifying their ordinal mapping. A later snapshot does not inherit keyless identities by ordinal, digest or guessed person match.

Operational map entries bind each source occurrence to its target table and internal ID. Allocate once; never merge cities, people, lookups or historical actors on equal names/passwords/numbers. Composite keys include every component. Historical actor text remains exact even when unresolved; a source user link does not activate or merge a web account. Visible project numbers remain original plus city. Full source column dispositions and reversible target projections are required before a mapping is executable.

## Deterministic batches and recovery

Logical interfaces are `FrozenSourceReader(manifest) -> ordered typed occurrences`, `OccurrenceMapper(approved mapping)`, `ImportBatchWriter`, and `RunCheckpointStore`. These are contracts, not prescribed Laravel classes or claims that supporting tables already exist. Production connections are outside this development contract; readers use isolated restored copies or immutable extraction artifacts.

1. Preflight validates the frozen manifest, approved schema/mapping hash, read-only source connection, target isolation, expected table coverage, numeric encoding vectors and exclusive run lease. Fail before writes on incompatibility. Keep private payloads outside repository logs.
2. Build the complete occurrence catalog and stable source-key map before resolving links. Read keyed rows in an immutable total order with source-compatible key semantics; use a frozen extraction ordinal as tie breaker when required. Keyless rows always use frozen ordinals. Persist the extraction boundary; OFFSET over a changing source is prohibited.
3. Write one bounded batch transaction containing occurrence registry entries, exact typed values, target rows/maps, durable exception references and the checkpoint for the highest contiguous completed occurrence. Checkpoint fields include manifest/mapping hashes, source/table, stage, last committed order token, batch ordinal, committed count, batch content digest and run/fencing identifier. No checkpoint may certify an incomplete row or advance past a failed occurrence.
4. Enforce one active writer per snapshot/mapping lane with a durable lease/fencing check at commit. Database unique constraints and full-key checks enforce retry identity. If commit succeeds but acknowledgement is lost, retry reads the durable checkpoint/map and verifies stored content instead of allocating another ID. A pre-commit failure rolls back the whole batch; a checkpoint failure rolls back its data writes. Separate target databases require an explicit durable outbox/recovery design before use.
5. Resolve relationships in a second stage after all row identities exist. Compute strongly connected components from declared and reviewed application links. Cycles and self-references use the same staged identities; never disable integrity checks globally or invent parents. Store original child values plus resolved target or explicit null/orphan/ambiguous/discriminator/sentinel status. Parent and child source/snapshot must match unless an individually approved cross-source relationship says otherwise. Unresolved non-null links remain exceptions.
6. Reconcile independently; then initialize number sequences from the maximum of 1, original maximum plus one and original AUTO_INCREMENT, with range checks. Reconciliation certifies both map uniqueness and sequence floors. Publish only through the separately authorized publication workflow after gate evidence. Import completion alone never changes source publication or account grants.

Resume first verifies lease, versions, manifest identity and last committed batch evidence. A completed occurrence with altered content is a blocking mismatch, not an UPDATE repair. Conflicting target IDs or a missing target behind a completed map stop for explicit recovery. A full successful rerun adds no records, relationships or file references. New snapshots stay unpublished until an accepted replacement/supersession policy exists; imported history and web-edited business identities must not be overwritten by guessed upserts.

Required synthetic recovery checks interrupt before writes, during a transaction, after commit before acknowledgement, and during relationship resolution; retry each twice. Compare complete counts/maps/values and unchanged internal IDs. Include digest-collision injection, concurrent-run fencing, repeated equal keyless rows, composite keys, same project numbers in five cities, source collation collisions, self/cyclic links and unresolved actors. These checks are requirements, not executed evidence.

## Authorized read-only attachment boundary

Use an opaque attachment reference ID at the HTTP boundary; never accept an FTP URL, hostname or filesystem path from a client. Resolve its owning record, source, city, snapshot and publication server-side. Check the current global account is active, has the owning city's current capability and may access the owning domain record. `projects.view` alone is not an approved universal file permission. Exact file capabilities/owner policies remain a P3.2 review requirement; deny until configured. Repeat authorization when a queued download starts and when downloaded; a long-lived URL must not bypass revocation.

Logical APIs: `AttachmentCatalog.find(referenceId) -> provenance and owner metadata`; `AttachmentAuthorizer.authorize(account, reference, action)`; `LegacyPathResolver.resolve(source, rawReference) -> validated storage locator or typed failure`; `ReadOnlyObjectStore.stat/openRead(locator)`; `BlobReader.openRead(source occurrence, column)`. Read adapters expose no write, rename, delete or upload operations. Server-side configuration selects an allowlisted storage endpoint/root per source. Do not extract credentials into documentation, browser state, queue payloads or logs. Development implementations use fake/local isolated storage; no live FTP probing is authorized here.

Keep original path bytes unchanged and store any resolver output separately. Apply one versioned, reversible legacy path mapping under the configured root; reject NUL/control bytes, traversal (including encoded separators/dot segments), unresolvable encodings, unauthorized absolute/drive/UNC paths and any attempt to change endpoint/root. Do not use a new project ID to reconstruct an old path. Constrain links/aliases and server-side path resolution to the root; if the server cannot guarantee confinement, that resolver is unaccepted. Path rejection retains the raw reference as restricted evidence; never silently repair it.

The file catalog follows every field/status in `phase-1/preservation-spec.md`: distinct attachment-reference and observed-object identities, source/snapshot/table/key/column/owner, raw reference/null/charset, storage location, original and resolved paths, bytes length/hash, observation stability, backup identity and explicit read state. Keep online, office, BLOB and backup observations separate. At minimum cover all five cities' `backgrounds.Image`, `file.File_Content`, `manualfile.Content`, `user.ProfilePicture`, plus `image.image_NewPath` and `manualfile.Path`; scan all remaining path/workflow mappings. Mixed BLOB/path rows preserve both without an invented precedence rule.

Stream bounded chunks without loading entire BLOBs/files into memory. Preserve bytes, null versus empty BLOB and source type. Downloads use private/no-store responses, safe server-generated Content-Disposition, escaped display names and nosniff; do not render arbitrary HTML/SVG inline. Handle disconnects/timeouts with closed streams and bounded retries. Keep missing, unreadable, unsafe, null, conflict and changed-during-read outcomes distinct internally; public errors reveal neither paths nor storage credentials. Audit IDs/outcomes, never payloads or raw private paths.

Every hash claim requires immutable storage or pre/post stability evidence; equal size/mtime alone cannot prove absence of same-size replacement. Hash office and online objects independently. An object that changes during streaming is not verified. Existing FTP is not its own backup: independently back up, restore into isolated storage and compare every required length/hash. Missing/conflicting objects need explicit disposition and truthful preservation statements. Deployment-host FTP connectivity/transport and cutover backup are later acceptance checks, not local mock results. Upload work uses isolated test storage and a new source-qualified collision-resistant namespace; no legacy overwrite.

## Independent reconciler and evidence

The reconciler uses separate source and target readers and independently implemented comparisons. It may consume the approved schema/mapping specification and immutable manifests, but must not call importer serializers, normalizers, row digest builders or reported success counters as its oracle. Hash aggregate shortcuts cannot replace per-cell and relationship coverage. Synthetic deliberate corruption must prove it detects a wrong value, swapped city mapping, duplicate omission, broken link, changed BLOB and corrupted checkpoint.

For every source table/column, enumerate source occurrences directly and reverse target mappings. Prove each occurrence has exactly its prescribed target disposition, no extra target occurrence, no many-to-one collapse, correct source/city/snapshot and complete preservation. Re-extract and compare exact integer/decimal/date/text/BLOB semantics in the P1 preservation specification. FLOAT/DOUBLE require validated binary protocol extraction and width/bit comparisons; display casts and epsilon tolerances do not certify them. Detect NULL/empty/zero, CHAR padding/retrieval limits, invalid dates, signed zero and Arabic sequence changes explicitly.

Independently resolve each original child tuple under source semantics, compare null/discriminator/sentinel handling, and reverse-map every resolved target parent to the expected source/snapshot/key. Count all unresolved links and anomalies; a preexisting source anomaly is explained evidence, not a repaired fact. Verify historical authors separately from login activation. Compare report selected identities, exact inputs and totals by city/currency under independently traced desktop formulas; unresolved formula rules block those report claims. Do not combine currencies.

Each run produces a restricted per-occurrence evidence bundle and a safe aggregate report: versions/hashes, observed source and target counts per city/table, column/relationship/file coverage, mismatch categories/counts, anomaly decisions, report definitions/totals, timings and run outcome. Restricted evidence includes stable exception IDs and original locators; public reports contain no raw personal values, paths, credentials or blobs. A mismatch is closed only by a linked verified rerun or an explicit reviewed disposition stating the preservation/workflow gap. No automatic waiver, truncation or repair.

## Acceptance boundary

P3.0 requires independently reviewed complete physical mappings and user schema approval before dependent domain migrations. P3.1 requires executable importer and all deterministic/rerun/interruption checks. P3.2 requires real authorization/path/stream tests using isolated fixtures plus later storage/backup verification. P3.3 requires independent full counts, values, links, BLOB/file and report evidence with zero unexplained mismatches. P3.4 requires an isolated five-city full rehearsal, timing and explicit anomaly dispositions. This document satisfies none of those runtime gates by itself.
